## 二、问题清单（按严重程度）

### P0 — 安全与正确性（必须修复）

#### P0-1 敏感用户操作存在横向越权风险

- **位置**：
  - `service/src/api/v1/user_router.py:105-115`（重置他人密码）
  - `service/src/api/v1/user_router.py:117-127`（修改他人状态）
  - `service/src/api/v1/user_router.py:140-149`（分配角色）
- **现状**：三个端点仅校验 `require_permission("user:edit")`，**未校验操作对象归属**。
- **风险**：任何持有 `user:edit` 权限的普通管理员，都可以重置**超级管理员**的密码、禁用超级管理员账号、或给自己分配高权限角色 → 构成**横向越权 + 提权**攻击面。
- **修复方向**：在路由层注入操作者身份，当**操作对象是超级用户**时，要求操作者自身也必须是超级用户；同时禁止操作者通过 `assign-role` 为自己提权。

#### P0-2 批量删除时缓存失效为循环调用（隐式 N+1）

- **位置**：`service/src/application/services/user_service.py:141-146`
  ```python
  deleted_count = await self.repo.batch_delete(user_ids)   # 数据库：1 次批量删除
  for uid in user_ids:
      await self._invalidate_user_cache(uid)               # 缓存：N 次 × 2 个 key
  ```
- **风险**：数据库侧已用 `IN` 批量删除，但缓存失效退化为逐条循环，每次循环产生 2 次 Redis 往返（`invalidate_user_info` + `invalidate_user_permissions`）。批量删除 500 个用户 = **1000 次 Redis 往返**，是典型的隐式 N+1。
- **修复方向**：在 `CachePort` 新增批量失效接口，一次调用完成全部 key 失效。

#### P0-3 代码规范违规（唯一 lint 错误）

- **位置**：`service/src/infrastructure/repositories/dictionary_repository.py:67`（行宽 122 > 120）
- **风险**：CI 门禁失败风险；配置声明行宽 320 但 ruff 规则实际为 120，**配置与规则不一致**是根因。
- **修复方向**：修正超长行；统一 `pyproject.toml` 与 `CODEBUDDY.md` 中的行宽声明。

### P1 — 架构与可维护性（应当修复）

#### P1-1 应用服务层缺少真实单元测试，2007 用例存在"虚假繁荣"

- **位置**：
  - `service/tests/unit/application/` 下**仅有 `dto/` 子目录，无任何 services 测试**
  - `service/tests/unit/api/v1/test_user_router.py:62-79` 用 `AsyncMock()` 整体替换 service 并返回写死的 `model_dump()`
  - 119 个 unit 文件中共 **138 处** `MagicMock` / `@patch`
- **风险**：业务语义（用户名冲突、权限拒绝、密码校验失败、缓存失效、批量删除计数）几乎**只靠 16 个集成测试**兜底。一旦 service 逻辑回归，单元测试**不会报错** —— 2007 的数字掩盖了真实覆盖缺口。
- **修复方向**：为 `application/services/*` 补充**不 mock 业务逻辑**的真实单元测试，仅替换最外层仓储为内存实现，断言业务返回值与异常类型。

#### P1-2 前端 API 层类型全面退化（`any` 泛滥）

- **位置**：
  - `web/src/api/base.ts:4,16,23,44`：`ResultTable<T = any>`、`Result<T = any>`、`PageParams` 含 `[key: string]: any`，`BaseApi` 所有方法 `<T = any>`
  - `web/src/api/user.ts:76,81` 等大量 `data?: object` 无结构化类型
  - `web/src/composables/useCrudTable.ts:35,43`：`dataList: Ref<any[]>`、`row: any`
  - 全项目 `any` 共 **122 处**，另有 **12 处** `@ts-ignore`
- **风险**：`vue-tsc` 通过是假象 —— 因为类型全是 `any`，类型检查**实际未生效**。字段改名、接口变更无法被编译器捕获，只能靠运行时崩溃暴露。
- **修复方向**：为各业务实体定义 `interface`，将 `BaseApi` 泛型化（`BaseApi<TList, TDetail, TCreate, TUpdate>`），消除 `api/` 目录下的 `any`。

#### P1-3 12 个 hook 重复实现 CRUD 表格逻辑，已有抽象未被采纳

- **位置**：`useCrudTable` 已存在且被 `system/role` 采用，但其余 **11 个 hook** 各自重写 `onSearch / resetForm / handleSizeChange / handleCurrentChange / pagination = reactive`：

  | 文件 | 行数 |
  |---|---|
  | `views/system/user/utils/hook.tsx` | 598 |
  | `views/system/dictionary/utils/hook.tsx` | 415 |
  | `views/system/menu/utils/hook.tsx` | 304 |
  | `views/system/ip-rule/hook.tsx` | 269 |
  | `views/system/dept/utils/hook.tsx` | 227 |
  | `views/system/role/utils/hook.tsx` | 209（已用 useCrudTable） |
  | `views/system/config/hook.tsx` | 212 |
  | `views/monitor/logs/system/hook.tsx` | 193 |
  | `views/monitor/logs/operation/hook.tsx` | 188 |
  | `views/system/permission/hook.tsx` | 167 |
  | `views/monitor/logs/login/hook.tsx` | 180 |
  | `views/monitor/online/hook.tsx` | 125 |
  | **合计** | **3,087 行** |

- **风险**：分页字段、loading 语义、错误处理在 11 处**各自演化**，改一处需同步 11 处，是典型的复制粘贴债务。
- **修复方向**：将分页/搜索/重置逻辑统一收敛到 `useCrudTable`，各 hook 只保留差异化的 columns 与特殊操作。

#### P1-4 定时器和伪延迟的反模式

- **位置**：
  - `web/src/views/login/utils/verifyCode.ts:22`：`setInterval` 仅在 `start/end` 内清理，**组件卸载时未 `clearInterval`**，倒计时泄漏
  - `web/src/views/monitor/online/hook.tsx:97`、`views/account-settings/components/SecurityLog.vue:66`：`setTimeout(..., 200/500)` **人为模拟 loading 延迟**
- **风险**：切换页面后定时器继续运行；伪延迟拖慢真实响应速度，掩盖真实性能问题。

### P2 — 测试覆盖与体验（建议修复）

#### P2-1 端到端测试覆盖严重不足

- **位置**：`web/e2e/` 仅 `login.spec.ts` 一个文件
- **现状**：以下模块**零 E2E 覆盖**：用户管理、角色管理、菜单管理、部门管理、字典管理、IP 规则、系统配置、权限分配、在线用户、三类日志（登录/操作/系统）、账户设置。
- **修复方向**：为核心 CRUD 流程补充 E2E 用例。

#### P2-2 后端 UI 自动化脚本无法运行

- **位置**：`service/tests/ui_test.py`（587 行，覆盖全部页面的 Playwright 脚本）
- **现状**：`service/.venv` 中**未安装 playwright**，`pytest` 收集阶段直接 `ModuleNotFoundError` 中断。
- **修复方向**：安装 playwright 至后端虚拟环境，并从默认收集路径中隔离（该脚本依赖外部服务，不应混入单元测试）。

#### P2-3 敏感 Token 存储于 localStorage

- **位置**：`web/src/utils/auth.ts:77-85`：`setToken` 将 `refreshToken`（长期有效）、`roles`、`permissions` 写入 `storageLocal`
- **风险**：`storageLocal` 基于 localStorage，任意 XSS 均可读取 refreshToken 并长期伪造会话；`TokenKey` Cookie 由 `js-cookie` 设置，非 httpOnly。
- **修复方向**：refreshToken 迁移至 httpOnly Cookie（需后端配合）；localStorage 仅保留非敏感 UI 状态。
- **说明**：此项需前后端协同改造，本次列为**建议项**，不纳入自动修复范围，避免过度改动引入回归风险。

## 5.3 其他改进（随本次一并提交）

- **后端**：`tests/unit/fakes.py` 内存仓储补齐数据权限范围过滤（`scope_dept_ids` / `scope_user_id`），与真实仓储语义一致；`get_count` 不再依赖 `get_all` 分页，语义更准确。
- **前端 API 类型化**（对应初版 P1-2）：`BaseApi` 泛型化、`SystemNotice` 实体与 `AnyRow` 联合类型补全、各 API 参数由 `object` 收敛为 `Record<string, unknown>`、`resetPassword`/`assignUserRole` 等入参具名化、角色新增 `dataScope`/`deptIds` 字段。

## 5.4 E2E 稳定性经验（重要）

- **必须串行执行**（`--workers=1`）：默认并发会在 Windows 触发 `WebSocket ERR_NO_BUFFER_SPACE`，造成冒烟/CRUD **假失败**（单独跑却通过）。
- **必须设置 `CODEBUDDY_SAFE_DELETE_ENABLED=0`**：Playwright 清理 `test-results`、vite 清理 `dist` 均会触发批量删除守卫而中止。
- 测试残留数据会导致后续运行反复失败，CRUD 用例统一用唯一名 + `afterAll` API 兜底清理。
