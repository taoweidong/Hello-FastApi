## 一、架构现状分析

### 1.1 分层结构（实测）

```
src/
├── api/            41 文件 / 2,437 行   路由层（12 个 Routable + 1 个 ws APIRouter）
│   ├── v1/                              业务路由
│   ├── dependencies/                    组合根（每服务一个工厂）
│   └── common/                          响应构造
├── application/    31 文件 / 4,533 行   用例层（12 个 service + DTO + mapper）
├── domain/         34 文件 / 3,321 行   领域层（实体/仓储接口/端口/领域服务）
├── infrastructure/ 56 文件 / 4,789 行   基础设施（SQLModel 仓储/Redis/HTTP 中间件）
└── config/          3 文件 /   254 行   配置
```

**依赖方向实测（本次扫描）：全绿。**

- `domain/` 对 application/infrastructure/api 的导入数为 **0**；
- `application/` 对 infrastructure 的导入数为 **0**（RealtimePort 落地后）；
- `api/dependencies/` 中的 infrastructure 导入全部发生在**组合根工厂**内——这是依赖倒置的正确落点。

**结论：分层骨架健康，端口-适配器模式（CachePort / RealtimePort / LoggingPort / IPFilterPort）执行到位。架构问题不在"方向"，而在"一致性"。**

### 1.2 请求生命周期（当前实现）

```
Request → SlowAPI 限流 → IP 过滤 → 登录限流 → 请求日志 → CORS（执行序）
        → Router（classy-fastapi，权限经 require_permission 依赖链）
        → Service（事务边界 = get_db 请求级单事务）
        → Repository（共享同一 AsyncSession）→ commit on success / rollback on error
```

事务模型：请求级单事务 + "所有仓储共享同一 session" 的**隐式约定**（由 13 个工厂全部注入 `Depends(get_db)` 保证）。约定目前成立，但零文档、零断言，已有现实代价（见 2.3）。

### 1.3 变更放大系数（可维护性的核心指标）

新增一个标准 CRUD 模块需触碰 **≈13 个文件 / 600-700 行**，其中：

- 3 个纯注册点（`dependencies/__init__.py`、`api/v1/__init__.py`、`models/__init__.py`）——靠人肉记忆，漏注册不报错（路由不出现/表未建）；
- **约 40% 是同一字段跨 3 层的手抄**（DTO→实体→ORM→mapper 四处 kwarg 复写）。以 user 域为例，新增一个字段需改 15 处、7 个文件；漏改后果各异且安静（漏 `to_domain` 读不出、漏 `from_domain` 写库丢列、漏 mapper API 不返回）。

### 2.3 事务约定的脆弱性（含一个未知的真实缺陷）

**缺陷实证：登录失败日志被回滚吞掉。** `auth_service.login` 失败路径先 `_write_login_log()` 再 `raise UnauthorizedError`（`auth_service.py:72-77`）；`create_login_log` 只 flush 不 commit；异常触发 `get_db` 整体 rollback → **安全审计最需要的"暴力破解失败记录"恰好被丢弃**。这是隐式 UoW 的现实代价：观测类副作用写库与业务写库共享事务边界。

其他脆弱点：新增工厂若自建 session，事务边界静默分裂、无任何报警；"先查重再写"依赖同 session flush 可见性，约定未写下来。

**建议（按成本递增）**：
1. 约定文档化（`base.py` docstring + `dependencies/__init__.py`）+ `get_repositories(db) -> RepoBundle` 聚合工厂，杜绝新工厂忘用同一 db；
2. 登录日志等观测类写入改用独立短会话（不受业务回滚牵连）；
3. 显式 UoW 延后到服务数量翻倍时再评估（当前 12 个服务，前两项已消除 90% 踩坑面）。

### 2.4 可读性细节

**加分项（保持）**：注释质量高且多为"解释为什么"（`base.py:138` 的事故记录、`settings.py:222` 的 pydantic-settings 陷阱、`cache_service.py:484` 的 ceil 论证）；无 print、无裸 except 扩散；EM 参数化消息已覆盖 12 个文件。

**扣分项**：
- **mypy"通过"是假象**：`mypy.ini:60-68` 把 application/infrastructure/api 三层全部 `ignore_errors=True`，严格模式只覆盖 domain。后果实证：`log_service.py:38,55,66` 参数完全无类型；55 处 `type: ignore` 中 52 处集中在 repositories（`session.exec(sa_update)` 签名噪音），采纳"基类统一 update"可消约 2/3；
- `CachePort` 的权限条目/会话信息全是 `dict[str, Any]`（11 处）——接口签名最弱一环，应定义 TypedDict；
- 命名：`DeptRouter` vs `DepartmentService` 缩写不一致；repo 引用名 10 种。

### 2.5 测试基础设施

- **串行 2091 用例 ≈117s，每用例常数 ≈56ms**——根因是根级 conftest 对**每个**测试（含不碰 DB 的纯逻辑单测）执行 create_all+drop_all（17+ 张表）。线性恶化：每 +100 用例 ≈ +5.6s，5000 用例时 CI 不可接受。**unit 级 conftest 覆盖掉 DB autouse 可立即回收约 2/3 时间**；
- **fakes.py 与真实仓储语义漂移（实锤）**：fake 的 `username in u.username` 是子串匹配，真实 `_apply_filters` 是等值匹配——基于 fake 的"模糊搜索"测试在生产是精确匹配，测试通过但行为不同；`assign_menus_to_role` 等硬编码空实现；`RecordingCacheService` 未继承 CachePort（接口加方法不报错）；
- 45 个测试文件用 AsyncMock、仅 2 个用 fakes——替身双轨制，建议补"fake vs 真实仓储契约测试"堵死漂移通道。

### 2.6 配置卫生

- `api/constants.py:8` 的 `DEFAULT_PAGE_SIZE=20 / MAX_PAGE_SIZE=100` **零业务引用**（仅同义反复的自断言测试），而 DTO 实际 default=10——删或实引；
- 分页字段字面量在 7+ 处重复（`log_dto.py` 三个 QueryDTO 各抄一遍），应抽 `BaseListQueryDTO`；
- 头像扩展名集合与 2MB 限制硬编码在 `user_router.py:32`；
- TTL/环境链卫生良好（保持）。

### 2.7 死代码

`response_builder.py` 的 `error_response`/`page_response`（自注释"旧版"）全库零调用，连带其测试用例——删除。

| 子维度 | 评级 | 一句话 |
|---|---|---|

| 测试基础设施 | **B+** | 金字塔完整；DDL 开销与 fake 语义漂移待治 |

**瓶颈结论：架构设计不是问题，一致性与转换层是。** 未达 A 的路径不在引入新框架/新抽象，而在"把已经做对的事统一成唯一写法"。

## 四、优化路线（按投入产出排序）

### 第二批：结构（~3 天）

5. **拆 user_service / auth_service**：抽 `AuthorizationService`（权限校验 + 数据范围解析，每请求热路径可独立测试）；路由树构建归 menu 域；`_expires_iso()` 去重；登录观测（日志+会话登记）独立并**改用独立短会话**（顺带修复失败日志回滚丢失）；文档化 UoW 约定 + `RepoBundle` 聚合工厂。
6. **CachePort 窄接口化**：按消费方拆 4 个窄 Port，`CacheService` 实现全部；`OnlineSessionStore` 独立。

### 第三批：转换层收敛（~3-4 天，最大化长期收益）

7. 定死唯一转换落点（service 尾部 `_to_response` 或统一 mapper），log/ip_rule/auth 的 router 层转换下沉；
8. **response_model 泛型实参化**（`ApiResponse[UserResponseDTO]`，router 直接返回 DTO）——OpenAPI 文档从 0 字段到完整，响应重获校验；
9. `to_domain/from_domain` 收敛为基类泛型实现（字段同构，手抄纯属复制）；基类吸收 7 份 update 覆盖（连带消 ~20 个 `type: ignore`）；逐步放开 mypy 对 application/infrastructure 层的 ignore。
10. 里程碑验收：新增 CRUD 模块的触碰文件 13 → 7-8 个，字段手抄点 15 → ~9 个。

### 不建议做的

- **不要**引入显式 UoW/Event sourcing/CQRS 等重抽象——当前 12 个服务的规模下样板成本 > 收益；
- **不要**为消 `type: ignore` 而放弃 `sa_update` 写回 `session.exec` 的现有方案——先统一到基类再评估；
- **不要**把 fakes.py 换成全真实仓储——内存替身对单测速度的价值真实存在，要修的是"契约对齐"而非"替换"。
