## 重要经验：E2E flaky 根因定位方法

三轮全量 E2E 失败用例**均不同**且单独复跑全部通过 → 判为 flaky。用 `git stash push -- <文件>` 做 A/B 对照，确认与代码无关。

**根因**：Redis（127.0.0.1:6379，v3.2.100）在 E2E 启动初期未就绪，后端走降级路径且每次缓存操作等一次连接超时 → 单请求 3.2s（日志 `POST /api/system/login | 200 | 3250.79ms`）。E2E 的 `networkidle` + 10s 断言均为临界值，随机超时。

**排查顺序**（有效）：看后端日志找慢请求 → 看 Redis 端口/连接 → 单测 Redis 读写（`redis.from_url(...).ping()`，注意项目已配 `protocol=2`，RESP3 假设不成立）→ 确认健康后重启服务复跑。

**E2E 前置检查清单（新增）**：跑全量 E2E 前必须先确认 `netstat` 6379 LISTENING 且 `redis.ping()` 通，否则会得到假失败。

## 全量测试（pytest 2171 + E2E 51/51）挖出的真实缺陷

### 1. dev.db schema drift：`sys_userloginlog` 缺 `username` 列 → 登录日志接口 500

- 堆栈：`sqlalchemy.exc.OperationalError: no such column: sys_userloginlog.username`
- **根因形态（重要）**：`alembic current` 显示已是最新 head（`c4d5e6f7a8b9`），但该迁移的 DDL **从未真正执行**——「**版本戳超前、结构落后**」。而 lifespan 走 `init_db()`（`create_all`），只建缺失表、**不会 ALTER 已存在表**，所以模型后加的 `username` 列一直没落到 dev.db。
- **为什么 pytest 发现不了**：测试用 `.env.testing` 独立库，每用例 `create_all/drop_all`，schema 永远最新；只有走 dev.db 的 E2E 会暴露。⇒ 「测试全绿」不等于「dev 库结构正确」。
- 修复（本地数据修复）：先 `cp sql/dev.db` 备份 → `alembic downgrade a3b5c7d9e1f2`（回退版本戳，迁移本身幂等）→ `alembic upgrade head`。
- 表名注意：登录日志表实际叫 **`sys_userloginlog`**（不是 `sys_login_logs`，我一开始查错名字得出错误结论）。
- 根治仍是方案文档 B5：lifespan 改 `alembic upgrade head`。

### 2. 前端 4 个 monitor hook 无 try/finally → 后端一报错 UI 永久转圈

`monitor/logs/{login,operation,system}/hook.tsx` + `monitor/online/hook.tsx` 的 `onSearch` 在 `await` 后才置 `loading=false`，接口异常时 axios reject 直接跳过 → 搜索按钮永久 `disabled`。已统一改 `try/finally`。**「后端故障被放大成前端假死」的典型链路**，排查时看到按钮卡 is-loading 要优先查后端是否 5xx。

### 3. 自查引入的回归（教训）

清理 `console.log` 时把 `Profile.vue` 的 else 分支写成 `return false`，使 `formEl.validate` 回调返回 `Promise<boolean>`，与 Element Plus `FormValidateCallback`（`void | Promise<void>``）不兼容 → typecheck TS2345。
**教训**：`pnpm typecheck 2>&1 | tail` 这种管道会吞掉退出码，`&&` 后面的命令仍会执行，导致"明明失败了却显示 OK"。必须用 `> log 2>&1; echo "exit=$?"` 拿真实退出码。
