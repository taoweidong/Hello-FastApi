## 重要经验：E2E flaky 根因定位方法

三轮全量 E2E 失败用例**均不同**且单独复跑全部通过 → 判为 flaky。用 `git stash push -- <文件>` 做 A/B 对照，确认与代码无关。

**根因**：Redis（127.0.0.1:6379，v3.2.100）在 E2E 启动初期未就绪，后端走降级路径且每次缓存操作等一次连接超时 → 单请求 3.2s（日志 `POST /api/system/login | 200 | 3250.79ms`）。E2E 的 `networkidle` + 10s 断言均为临界值，随机超时。

**排查顺序**（有效）：看后端日志找慢请求 → 看 Redis 端口/连接 → 单测 Redis 读写（`redis.from_url(...).ping()`，注意项目已配 `protocol=2`，RESP3 假设不成立）→ 确认健康后重启服务复跑。

**E2E 前置检查清单（新增）**：跑全量 E2E 前必须先确认 `netstat` 6379 LISTENING 且 `redis.ping()` 通，否则会得到假失败。
